# Windows maintainer guide

Authoritative guidance for Windows-only behavior, deployment, virtual displays and stitch input. Read this file before changing those areas.

[Back to AGENTS.md](../../AGENTS.md)

## Windows specifics (easy to get wrong)

- `sender` links as a **console** subsystem app (logs + interactive prompts + Ctrl+C). `receiver` and `app` link with `-mwindows` (GUI, stdout discarded).
- `res/admin.manifest` declares **PerMonitorV2 DPI awareness** for both sender and app. The sender must be DPI-aware: in a DPI-unaware process Windows virtualises `GetSystemMetrics`/`GetMonitorInfo`/GDI capture coordinates (a 3840x2160 VDD is reported as 2560x1440 at 150 %), which silently turns the receiver-matched extend path into an upscaled stream. Don't remove it — the GUI's `g_uiScale` assumes per-monitor awareness too.
- **Windows capture is DXGI Desktop Duplication first, GDI second** (`src/capture_dda.cpp`, linked into sender only with `-ld3d11 -ldxgi`). Measured on the project laptop (Windows 11 26200, 60 Hz): GDI `GetDC(NULL)` + `BitBlt` costs **~17 ms for anything up to 1080p and ~33 ms above it** — it is quantised to 1–2 compositor refresh intervals and is NOT proportional to the requested rect (640x480 and 1280x720 also cost ~17 ms). Duplication costs only the staging copy: ~2–6 ms (map + row copy) and never waits a refresh. This was the dominant source of mouse lag in extend mode. Invariants: the duplicated image **excludes the cursor**, so `capture_dda.cpp` keeps a clean BGRA background and composites `GetCursorInfo` + `DrawIconEx` into a 32-bit top-down DIB on every produced frame; a cursor move **inside the captured output** alone is reported as a new frame (otherwise the remote pointer freezes on a static desktop), while moves on another monitor or a hidden cursor produce nothing. The cursor is drawn when its image rectangle (hotspot ± cursor size) intersects the output, so a half-off cursor at the screen edge still appears. On open the background is seeded with **one GDI BitBlt copy**, because a static desktop can keep delivering only empty `LastPresentTime == 0` frames; that seed gives the session its first image, and a 3 s watchdog falls back to GDI only if even the seed failed. Frames are packed BGRA→**BGR24** by the sender before encoding — do NOT feed BGRA to swscale: its BGRA→YUV kernel differs from the BGR24 kernel (synthetic input: max 29, mean ~3 levels), while the pack + `encodeBGR24` path is byte-identical to GDI output. Selection: `ddaOpen(g_cap_device)` matches `DXGI_OUTPUT_DESC.DeviceName` to the VDD's GDI name (extend) or the output containing (0,0) (mirror), and the D3D11 device is created on the **owning adapter**. A new duplication session can hand back an **empty frame first** (`LastPresentTime == 0`, black texture, observed on 4 of 5 opens); the module releases and ignores it and keeps waiting — mapping it produced a black first frame. If no real image arrives within 3 s the caller falls back to GDI rather than showing black forever. Any failure (output not duplicable — e.g. an IDD that DXGI does not expose, non-BGRA8/HDR format, exclusive duplicator, size mismatch) silently leaves the GDI path in place; `MIVARA_CAPTURE=gdi` forces GDI for A/B tests. `DXGI_ERROR_ACCESS_LOST` (UAC secure desktop, mode change, driver reset) drops to GDI but is **retried with a 2 s → 60 s exponential backoff** (also when the first open fails, so a late-appearing VDD can still be picked up); `MIVARA_CAPTURE=gdi` is never retried. A VDD resize reopens duplication at the new size. The loop fails open: when neither desktop nor cursor changed, it sends `CTRL_MARKER + CTRL_FORCE_IDR` (ignored by the receiver) every **500 ms** — enough to keep the receiver's 30 s read timeout away while letting its SDL event pump run often enough that ESC/close respond — and still emits the periodic `STAT` line so the GUI counters do not freeze. Frame pacing uses the `ddaWait()` deadline instead of `sleep_for`, because Windows' default sleep granularity (~15.6 ms) would cap a 60 FPS loop well below 60. A rotated output whose duplicated texture dimensions differ from its `ModeDesc` is refused and falls back to GDI (which handles rotation). `gpu_accelerate.c`/`codec.cpp` are unchanged for this path; `codec.h`'s `encodeBGR24` is the shared sink for GDI and DDA frames.
- **Original B application icon** — `res/mivara-mark.svg` is the editable transparent/black mark; `res/mivara-app.svg` is the `#2F6FEC`-background, white-mark application source. Preserve the original B exactly: `viewBox="0 0 256 256"`, two rounded outline rectangles and the `front-cutout` mask geometry (including the 16-unit stroke); never substitute another logo or redraw/thicken it. Only the **background tile** is rounded, and its `rx="54"` is not a free parameter: the white frame's outer edge sits at 24..232 with `rx=30`, so a concentric tile needs `rx = 24 + 30 = 54`. That keeps the edge and corner gutters equal at 24 units (measured: `rx` 48/52/56/60 all skew the corner gutter by 45–54 %). The four corners outside the arc are transparent, which is why the PNG/ICO rasters carry real alpha; the mark itself stays white-on-blue inside the tile, so it never depends on the desktop background. `res/mivara-{16,32,48,256}.png` are rendered from the app SVG, and `res/mivara.ico` contains 16/32/48 as 32-bit BMP entries plus 256 as PNG. `res/admin.rc` embeds the ICO as RT_ICON resource ID 1 alongside the manifest; `src/tray.cpp` loads that ID through `GetModuleHandleW(nullptr)` and falls back to `IDI_APPLICATION`. Keep `res/mivara.ico` in the `RES_ADMIN` dependencies. `src/logo_icon.h` embeds the actual 32 PNG's RGBA bytes and creates a 32x32, pitch-128 `SDL_PIXELFORMAT_RGBA32` surface with `SDL_CreateRGBSurfaceWithFormatFrom`; its pixel array must remain static because the surface references external storage rather than owning a copy.
- **Stitch (software KVM) input plumbing** — `kvm.cpp` is Windows-only (`kvmSupported()` is inline in `kvm.h` so `app` needs no link). Controller: `WH_MOUSE_LL`/`WH_KEYBOARD_LL` + a hidden top-level window with `RIDEV_INPUTSINK` Raw Input; **never do socket I/O inside a hook** (overrunning `LowLevelHooksTimeout` silently unhooks it) — events go through an SPSC ring to a drain thread, which posts a disconnect back to the message loop. Edge crossing must use `WM_INPUT` relative deltas: once the cursor is clamped at the virtual-desktop edge the hook's `pt` stops changing. Nothing but the ring push may run inside a hook callback: `ShowCursor`/`SetCursorPos`/`std::cout` (panic hotkey, mode changes) are deferred to the message loop with `PostMessage`; the button *state* table is updated in both Local and Remote (a press or release that straddles a mode switch would otherwise be replayed as a phantom drag or never re-armed), and both hooks pass `*_INJECTED` input through untouched instead of forwarding it. Target: the configured 接收策略 first (protocol v2 — open, password proof, or the receiver's manual-approval prompt; when the receiver runs without the app hooks a topmost `MessageBoxW`, default No, 30 s auto-dismiss + shutdown watcher is the fallback), then `SendInput` (absolute + `MOUSEEVENTF_VIRTUALDESK`, scan-code keys). The 8084 authorization exchange is **on the session thread before any event is read** — never start injecting before it completes, and never add an 8084-only path that skips it. Both roles poll the caller's `g_running` as **true = running**. `-luser32` is in `SENDER_LIBS`/`RECEIVER_LIBS` for exactly this file. Elevation: a standalone `bin/receiver.exe` is not elevated, so injection stops at its integrity level (UIPI — no input into elevated windows, no secure-desktop input); launched from `app.exe` it inherits the GUI's `requireAdministrator` token and can reach elevated windows, which is why the receive policy matters. This is a behavior difference worth stating in the user docs, not a bug to "fix" by de-elevating a child Windows cannot easily de-elevate.
- **Stitch file drop (8085) is copy-only and opt-in.** The controller side is `src/drop.cpp` + `src/dropshell.cpp`; the target side resolves the folder under the release point and copies the staged items there. The controller cannot receive an ongoing Explorer `DoDragDrop` in its High-integrity process (UIPI blocks Medium Explorer from dropping onto a High window), so `bin/stitchcap.exe` is a separate **asInvoker** helper launched with the shell token (`CreateProcessWithTokenW`). It owns a **3-pixel topmost strip** on the shared edge, captures `CF_HDROP` in `DragEnter`, forwards the paths over a **pair of one-way named pipes** (one duplex handle would serialise the pending reader against every write — see the architecture guide), advertises `DROPEFFECT_COPY` from `DragEnter`/`DragOver` and returns `DROPEFFECT_NONE` from `Drop`; it never copies anything locally. The COPY verdict is mandatory: with NONE, OLE turns every release into `DragLeave` and never calls `Drop`, which also sends `NODRAG` and would discard the captured paths. The strip is deliberately 3 px so normal edge use is almost unaffected, but it is still a 3 px dead zone. The helper reports its integrity level; the controller accepts it only when it is no higher than the shell token it duplicated (Medium normally, High when Explorer itself is elevated). The pipes must carry an explicit Medium mandatory label plus a DACL for the interactive user: the sender is High and a default pipe inherits a High label, which MIC no-write-up denies to the Medium helper. If the helper cannot reach that level, the controller does not advertise the feature. The target resolves Explorer via `IShellWindows` → `IServiceProvider` → `IShellBrowser` → `QueryActiveShellView` → `IFolderView` (MinGW's `IFolderView` has no `ItemAt`, so the item cell is hit-tested with `GetItemPosition` + `GetSpacing`), and the desktop via `Progman`/`WorkerW` → `FOLDERID_Desktop`. The destination must be a local fixed drive, not a reparse point, and not a startup/system location; the staging directory is `%LOCALAPPDATA%\Mivara\Drop\<transfer>-<tick>-<seq>` (residue is swept when the 8085 listener starts), each file is verified with SHA-256, and the commit uses `SHFileOperationW` with `FOF_SILENT|FOF_NOCONFIRMATION|FOF_NOERRORUI|FOF_NOCONFIRMMKDIR|FOF_RENAMEONCOLLISION` and a unique name (never overwrite; the rename flag only covers a race during the copy). The default fallback destination is `%USERPROFILE%\Downloads\Mivara`; if Downloads is not on a local fixed drive or cannot be created, it becomes `%LOCALAPPDATA%\Mivara\Received`. The destination directory is reopened without delete sharing and pinned for the copy, which blocks a junction swap of the folder itself after validation; a swapped parent component remains a residual TOCTOU because `SHFileOperationW` cannot write relative to a handle. Shutdown is checked between top-level items, but `SHFileOperationW` itself is not interruptible. Per-top-level-item commit is not atomic: a partial commit is reported as an error with `items`/`failed` counts and may leave the failed item's partial data; never delete a destination by guessing. Never add a delete/move step: the source is opened read-only and is never modified. The release point is the target's screen coordinate sent over 8085; the 8084 event stream is untouched. The controller's transfer liveness is `g_drop_run` (true = continue, set by startFileDrop, cleared on panic/disconnect/teardown) — never hand dropSendFiles an inverted cancel flag. Saving 设置 with a changed 拖拽到边缘发送文件 toggle restarts the stitch session so the helper and the capability bit are re-negotiated (the peer consents again); the receiver's 允许对端发送文件 still applies live through `RX|reload`. Capture diagnostics: `MIVARA_DROP_TRACE=1` / `MIVARA_STITCHCAP_TRACE=1` write `%TEMP%\mivara-dropctl-trace.log` / `%TEMP%\mivara-stitchcap-trace.log` (see the protocol guide), and helperReader publishes `ready` before `hello` so the 3 s startup poll cannot misread a valid helper as over-privileged. Both directions are supported: the target also runs stitchcap on the edge facing the controller (opposite side) with a watcher that reports `KVM_EV_RDRAG` and sends the files to the controller's own 8085 listener (`DropHello.flags=DROP_FLAG_REVERSE`); the controller suppresses back-crossing while a reverse drag is live so the target's OLE drag can finish on release, and the receiving dropWorker resolves the reverse destination from `GetCursorPos` (its desktop edge after leaveRemote). The target also draws a drag ghost next to the injected cursor (`KVM_EV_DRAG_INFO` / `KVM_EV_DRAG_TEXT`) with a GDI DIB pushed by `UpdateLayeredWindow` — the session thread has no message pump, so never switch that overlay to `WM_PAINT`+`SetLayeredWindowAttributes`; `receiver` therefore links `-lgdi32`. The card shows the item's own shell image when both peers negotiate `KVM_FEATURE_DRAG_ICON`: the source calls `IShellItemImageFactory::GetImage` (thumbnail, falling back to the icon) **off the input/hook loop** — the controller's message loop only requests it and a worker posts the finished raster back, because a thumbnail provider on a network/cloud path can block for a long time; the target's reverse watcher uses a 250 ms bounded extraction (the 8085 copy, watcher join and session teardown must never wait on a provider), and the worker's own extraction is bounded at 800 ms so the controller's teardown join cannot hang. The image travels as `KVM_EV_DRAG_ICON_INFO`/`DATA` frames (max 48x48 from the source, receiver cap 64x64) and is composited into the cached card DIB; a missing/incomplete image keeps the page glyph. `SHCreateItemFromParsingName` needs the absolute backslash paths CF_HDROP supplies, and `GetDIBits` output alpha=0 means "opaque" for legacy DDB icon handlers. Old peers do not advertise the bit, so no unknown event ever reaches an old controller (whose drain loop disconnects on an unrecognised type). **A second, preferred path carries Explorer's exact drag image:** when both peers negotiate `KVM_FEATURE_DRAG_IMAGE` (16), `stitchcap.exe` reads the shell's `DragImageBits` in `DragEnter`. After OLE marshals the data object, the HGLOBAL is `u32 w, u32 h, i32 offset_x, i32 offset_y`, a 4/8-byte process-local HBITMAP slot, then `w*h` premultiplied BGRA pixels at the tail in **bottom-up DIB row order**; the handle is invalid in the helper but the tail pixels are intact, and the helper swaps whole rows to top-down (not a full buffer reverse, which would also mirror each row into a 180-degree rotation). The helper downsizes above `DROP_DRAG_IMAGE_MAX_PIXELS` (36,864 px), sends `IMG_BEGIN`/`IMG_CHUNK` (hex)/`IMG_END` before `FILES_END`, and the controller/target forward `KVM_EV_DRAG_IMAGE_INFO/DATA` so the peer blits the native image at `(cursor - offset)`. The reconstructed icon/name card is the fallback when the source provides no image (old peer, non-Explorer drag, oversized/malformed blob) or the sequence does not complete. After a commit, `dropPlaceIcons()` positions the new icons at the release point with `IFolderView::SelectAndPositionItems` unless the folder auto-arranges. The controller's reverse listener must use 8087 (`DROP_REVERSE_PORT`), never 8085 — the same machine usually runs `receiver.exe`, which owns 8085, and a failed bind left the token installed in a process that never served the port (every reverse transfer got `DROP_ERR_AUTH`). The session token is generated whenever either direction is enabled, never left all-zero on a reverse-only session, and back-crossing a left-button drag requires ~24 px accumulated pushback so a natural pullback no longer cancels the copy.
- **Independent file transfer (8086)** is not part of stitch and does not use `stitchcap.exe`, Explorer release-point resolution or the 8085 token. `filexfer.cpp` is shared by app + receiver and uses length-prefixed UTF-8 paths; `std::filesystem::u8path/u8string` remain for parsing/display, while the security boundary is `DirLock` handle-relative I/O. The root/base is opened with `CreateFileW(..., FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT)`; each child directory is opened with `NtCreateFile` and `OBJECT_ATTRIBUTES.RootDirectory`, `FILE_OPEN_REPARSE_POINT` and `FILE_DIRECTORY_FILE`, then checked for `FILE_ATTRIBUTE_REPARSE_POINT`. A directory that will receive a MKDIR requests `FILE_ADD_SUBDIRECTORY` on the **final** handle only (`DirLock::open(..., create_child=true)`); without it `NtCreateFile(RootDirectory=…)` returns `STATUS_ACCESS_DENIED` and remote folder creation always fails while POSIX passes. Folder creation uses the same pinned-parent handle with `FILE_CREATE | FILE_DIRECTORY_FILE`; `STATUS_OBJECT_NAME_COLLISION` maps to `FT_ERR_EXISTS`, and existing names are never replaced. LIST sets `hidden` from `FILE_ATTRIBUTE_HIDDEN` only (Explorer does not hide dotfiles) and `mtime` from `ftLastWriteTime` (FILETIME → unix seconds, clamped to `FILEXFER_MAX_MTIME`). UNC paths are split manually (`winSplitRoot`) because MinGW's `fs::path` treats `\\server\share` as relative and `fs::absolute` would rewrite it to a local drive; `GetFullPathNameW` is the path normalizer. Windows has no full relative-file API usable with synchronous ReadFile/WriteFile, so the final file is opened through its canonical path, and the live parent obtained from `GetFinalPathNameByHandleW` must be the same directory object as the pinned handle (volume serial + file index, not a string compare); a swapped ancestor or case-sensitive-directory substitution is rejected. Temporary files are created in the pinned directory with `CREATE_NEW` and verified the same way; commit renames the open temporary handle with `NtSetInformationFile(FileRenameInformation)` and `RootDirectory` (the Win32 `SetFileInformationByHandle` wrapper returns `ERROR_INVALID_PARAMETER` for a relative rename), so no-replace does not depend on `MoveFileW`. Directory listing also pins the directory with `DirLock` and enumerates it with `FindFirstFileW` on the `\\?\` path; `std::filesystem::directory_iterator`/`directory_entry::symlink_status` fail on such paths, so do not switch back to them. `apiPath` converts forward slashes before adding the `\\?\` prefix because that prefix disables separator normalization. `ntdll` is loaded with `GetProcAddress`, so no new link flag is needed. Junctions/mount points anywhere in the selected path are deliberately refused. Windows local-name rules (`<>:"|?*`, reserved names, trailing dot/space, 255 UTF-16 units) apply only to local writes (`validLocalName`), not to wire decoding. It uses SHA-256 and a no-replace commit; the POSIX path retains a same-directory temporary-name race, while the Windows rename acts on the open temporary handle. It has a separate default-off `file_transfer_accept` switch because authorization permits remote browse/read/write, not just an incoming copy. A GUI-launched receiver inherits the app's elevated token, so this permission includes elevated file access; never silently inherit `file_drop_accept` for it. The channel remains plaintext.
- SDL2_ttf needs a CJK font at runtime; `app.cpp` walks an ~11-path candidate list (`msyh.ttc`/`simhei.ttf`/NotoSansCJK/wqy/…) and exits with an error if none is found. Caveat: the list also contains non-CJK `DejaVuSans.ttf`, so on a machine with no CJK font the probe can "succeed" via DejaVu and render tofu instead of erroring.
- The runtime DLL closure must sit in `bin/` next to the exes. `make copy-dlls` resolves it with `objdump` over the import tables, **not `ldd`**: MSYS2's `ldd` debug-loads the target, and `CreateProcess` on the `requireAdministrator` `sender`/`app` fails with `ERROR_ELEVATION_REQUIRED`, so `ldd` silently reports nothing for exactly those two binaries and `SDL2_ttf.dll` / the newer FFmpeg closure never got copied. After adding a library, run `make copy-dlls` and verify the import closure with `objdump -p` (system DLLs and `api-ms-win-*` excluded).
- Extend mode needs the MttVDD indirect-display driver installed once (`vdd/install_vdd.ps1`). **Inno Setup is a 32-bit process**, so a bare `{sys}\WindowsPowerShell\...\powershell.exe` starts 32-bit PowerShell, where `%SystemRoot%\System32` is redirected to SysWOW64 and `pnputil.exe` "does not exist" (the installer then reports the VDD install failed). The .iss starts `{sysnative}\WindowsPowerShell\...` and the script self-boots through `Sysnative` when `[Environment]::Is64BitProcess` is false, so both the installer and a manual run from a 32-bit shell reach the real 64-bit pnputil. Do not remove either guard. Windows PowerShell 5.1's `Get-PnpDevice` has no `-HardwareId` parameter; `Get-MivaraVddDevice` must filter the `HardwareID` property through the pipeline so device detection works from the installer on a stock machine. The bundled DevCon has no `create` command; create the root-enumerated device with `devcon install <full INF path> Root\MttVDD` (no `@` prefix), and keep the existing-device guard because every `install` call creates a new devnode. The virtual display lifecycle lives in `src/vdd.cpp`/`vdd.h` (`vddStartup`/`vddShutdown`/`vddForceDetach`, CCD API + SetupAPI device enable/disable) and is linked into both `sender` and `app`. The VDD mode list is read by the driver **once at start-up** from `vdd_settings.xml` (registry `SettingsPath`/`VDDPATH` override first, else `%SystemRoot%\System32\drivers\UMDF\vdd_settings.xml`); a size absent from that list cannot be applied. `vddEnsureMode()` can append the receiver's exact size (numeric-only and even, bounded 320x240..7680x4320, session mutex, pristine `.mivara.bak`, unique temp + `ReplaceFile` which keeps the System32 ACL, in-memory rollback, re-read verification) but refuses to touch the file while any VDD CCD path is ACTIVE — that would yank a display a live session owns; `vddStartup(..., reloadFirst=true)` then does one disable/enable cycle (never while a path is active) so the UMDF stack re-reads the file; otherwise `vddStartup` enumerates the exposed modes and uses the closest aspect. The startup snapshot preserves the active non-MTT paths, sources, clone groups and modes; enabling the device may automatically clone physical targets, so detach only those MTT paths and restore the snapshot before attaching. Identify the MTT target by its `DISPLAY#MTT1337#` path, enumerate `QDC_ALL_PATHS`, and select a target-available path whose source is not occupied, preferring the MTT adapter's own source. Allocate a distinct clone group: a second target on a physical source or in the same clone group is mirroring, not Extend. Never apply a global `SDC_TOPOLOGY_EXTEND` or preserve the pre-enable MTT clone in the baseline. Resolve the GDI name from the accepted active CCD source and verify desktop attachment; check every GDI monitor index for MTT rather than assuming `Monitor0`. After sizing/positioning, read back both MTT independence and the non-MTT layout. Use `SDC_USE_SUPPLIED_DISPLAY_CONFIG | SDC_ALLOW_CHANGES | SDC_VIRTUAL_MODE_AWARE` without `SDC_SAVE_TO_DATABASE` so session changes are not persisted. Normal cleanup preserves the current non-MTT layout; a failed startup restores the saved pre-start baseline. The receiver aspect-fits the stream (black bars) instead of stretching, so a residual mismatch is never distortion. **Never break the Ctrl+C graceful path** — a hard exit leaves the virtual display attached to the user's desktop. Covered exit paths: normal end, send failure, Ctrl+C, console-window close (detaches inside the `CTRL_CLOSE_EVENT` handler), `atexit`. The GUI stops the sender over its stdin pipe (`STOP|mivara`) — a GUI parent cannot deliver Ctrl+C to a child console on current Windows, so this is the primary path. `GenerateConsoleCtrlEvent` remains only the fallback for the visible-console launch (no stdin pipe) and must use `CTRL_BREAK_EVENT` (Ctrl+Break is delivered where Ctrl+C is not), detaching with `FreeConsole` **before** the wait because the console teardown after the child exits would otherwise terminate the attached GUI. Hard-kill only after an 8 s timeout, and call `vddForceDetach()` as a safety net after a hard kill.
- A CCD detach alone leaves the monitor visible in Settings > Display — teardown MUST also disable the PnP device (hardware ID `Root\MttVDD`, instance `ROOT\DISPLAY\000x`; match on hardware IDs, never touch other vendors' virtual display adapters). Enabling/disabling requires elevation: `sender` and `app` embed a `requireAdministrator` manifest via `res/admin.rc` + `res/admin.manifest` (windres, see makefile `RES_ADMIN`). `receiver` is not elevated. Disable failure degrades gracefully (warn + CCD-only). A disabled device has no CCD path — `vddStartup` must enable the device **before** the `vddInstalled()` gate.
- **Tray + single instance** live in `src/tray.cpp` (Windows only, `-lshell32 -luser32` in `APP_LIBS`). The icon is owned by a dedicated thread with a message-only window (`HWND_MESSAGE`); tray callbacks only set atomics, and the SDL loop drains them once per frame (`trayTakeRequests`), so no tray callback ever touches SDL. Closing the main window hides it (`SDL_HideWindow`) while the receiver/sender children keep running; the log window is hidden and restored too. Consequences worth preserving: `SDL_QUIT` means "hide" only when the tray exists — otherwise it must still quit; `requestQuit()` is the single exit path (it sets `g_exit_requested` and posts `SDL_QUIT`, letting the loop save settings and clean children); an exit while a session is active asks for confirmation (`MessageBoxW`, `MB_DEFBUTTON2`, default = keep running); the first hide shows a one-time balloon and persists `tray_hint_shown`; hiding/quitting **must not** write `auto_receive` (and `allow_receive` is never persisted at all — the receive switch is runtime state). Single instance is the `Local\\Mivara.App.SingleInstance` mutex claimed **before** the SDL window is created. Waking the existing instance must not depend on the icon: the primary also creates the named event `Local\\Mivara.App.Show` and a small wait thread, and a second launch sets that event **and** still tries `FindWindowExW(HWND_MESSAGE, …)` + `kMsgShow` as a fallback, then exits. If `Shell_NotifyIconW(NIM_ADD)` fails, the message-only window and its loop stay alive as that fallback (`trayInit` returns false meaning "no icon", not "no IPC"), so the GUI must drain `trayTakeRequests()` unconditionally rather than gating it on `g_tray_ok`. `trayShutdown()` stops the wake thread, posts `WM_CLOSE` and joins — call it on **every** exit path after the children are stopped but before the SDL teardown (including the SDL_CreateWindow/Renderer failure path), and release the mutex last via `traySingleInstanceRelease()`.
- **Auto-start stays a Task Scheduler `onlogon` job with `/rl highest`** (`applyAutoStart` in `app.cpp`; task name `Mivara`, also removed by the installer's `[UninstallRun]`). `app.exe` and `sender.exe` embed `requireAdministrator`, so an `HKCU\...\Run` entry would re-trigger UAC at every logon; the scheduled task starts the app elevated and silently. The app registers/removes the task on 保存设置, reads the result back with `schtasks /query`, folds the real state into `config.ini`, and repairs a missing/leftover task at startup (`reconcileAutoStart`). `schtasks /delete` exits non-zero when the task is absent — never report that as a registration failure (check existence first).
- `scripts/*.bat` are convenience wrappers that launch `bin/` exes; `启动投屏发送.bat` takes the receiver IP as an argument.
