# Protocol maintainer guide

Authoritative guidance for wire protocols, runtime control channels, discovery and network behavior. Read this file before changing those areas.

[Back to AGENTS.md](../../AGENTS.md)

## Protocol constants (defined in `src/proto.h`)

- Handshake over TCP 8081 (**protocol v3**, all u32 network byte order, magic `0x54564853` 'TVHS', `TVHS_VERSION = 3`):
  - Request (sender→receiver) `HsRequestV2` **48 bytes**: magic, version=3, width, height, fps, mode, codec, codec_flags, bitrate_kbps, quality, gop_frames, reserved.
  - Challenge (receiver→sender) `HsAuthStart` **64 bytes**: magic `0x54564841` 'TVHA', version=2, mode (`AUTH_MODE_OPEN/PASSWORD/MANUAL`), kdf_iter, salt[16], nonce[32]. Sent for every policy; the salt/iter are filled (and meaningful) only in password mode.
  - Identity (sender→receiver) `HsRequestExtV3` **48 bytes**: magic 'TVHX', version=2, device[32] (UTF-8 hostname), flags, reserved.
  - Proof (sender→receiver, password only) `HsAuthProof` **40 bytes**: magic 'TVHA', version=2, proof[32].
  - Response (receiver→sender) `HsResponseV2` **36 bytes**: magic, version=3, recv_width, recv_height, status, codec, codec_flags, reserved[2].
  - Token (receiver→sender, `HS_OK` only) `HsResponseExtV3` **44 bytes**: magic `0x54564852` 'TVHR', version=2, token[32], flags.
  - `mode`: 0 = mirror, 1 = extend. `codec`: 0=raw 1=rle 2=h264 3=h265 4=av1. `status`: 0=ok 1=version 2=codec 3=dims 4=decoder 5=legacy 6=busy 7=auth 8=auth_timeout 9=denied 10=auth_config.
  - Receiver peeks 4 bytes first: non-TVHS magic ⇒ legacy peer, explicit error (no black screen). A pre-v3 request is answered `HS_ERR_VERSION` **before** the authorization exchange, so an old sender cannot bypass the policy.
  - Authorization is enforced at the receiver only. The proof is purpose-separated (`auth.h`):
    `purpose_key = HMAC-SHA256(PBKDF2(fold(pw), salt, iter), "Mivara/v1/auth-key" ‖ purpose)` and
    `proof = HMAC-SHA256(purpose_key, "Mivara/v1/auth-proof" ‖ purpose ‖ nonce ‖ raw HsRequestV2 ‖ raw HsRequestExtV3)`,
    with `purpose = 1` for 8081 video and `2` for 8084 stitch. `fold` is ASCII-only and locale-independent: `A`–`Z` become `a`–`z`, every other byte is unchanged, so passwords are case-insensitive. Record creation (`mivaraPasswordKey`), the 8081 sender and the 8084 stitch controller must all fold before PBKDF2; the receiver never sees the plaintext and never folds the stored record. The wire carries no password and the receiver stores only salt + PBKDF2 output + iter. New records use `MIVARA_AUTH_DEFAULT_ITER` (300000); existing records keep the count they were created with. Accepted `kdf_iter` is bounded by `HS_KDF_ITER_MIN/MAX` (10000–1000000); anything else is a corrupt record, refused `HS_ERR_AUTH_CONFIG` rather than downgraded. `HsResponseV2` is sent for denial/timeout/bad proof; a password policy whose record is missing or malformed refuses every connection (`HS_ERR_AUTH_CONFIG`) and never falls back to open or to a prompt. Purpose separation and the higher iteration count reduce cross-port replay and raw-key reuse but do **not** remove offline guessing or the credential-equivalence of a leaked `config.ini` — see SECURITY.md.
  - **Display-size probe (no version bump):** a normal `HsRequestV2` with `width=0 && height=0` asks only for `HsResponseV2.recv_width/recv_height`; the receiver answers with `status=HS_ERR_DIMS` and returns before creating a window, a decoder or an authorization exchange. The reply comes from a cache refreshed by the receiver's main thread (at most once per second while idle and again before/after every session, so a monitor change or dock replug is picked up without touching SDL from a worker), in physical pixels. No window appears and no client stats are recorded. Extend mode uses it to size the VDD before the real handshake.
  - **Session token:** an authorized 8081 session receives a random 32-byte, per-session token. The 8082 compute service and the 8083 port inspector read 32 bytes on connect **and re-check the token before every request** (including before 8083's expensive port listing and its kill operation), so a connection opened during a session loses access on its next request once the session ends, and a new connection presenting the old token is refused. `mivaraSessionTokenClearIf()` clears only the ending session's token.
  - **One session per process:** 8081 and 8084 share one active-session slot in `auth.cpp`. While either port has a session, the other answers `HS_ERR_BUSY` (8084 sends `HsResponseV2(HS_ERR_BUSY)`). An unauthenticated handshake never holds the slot: 8081/8084 pre-check the owner before the challenge, and claim it only after authorization succeeds — or, in manual mode, just before the prompt (a human decision must not be stolen by the other port).
- Stream packets: `[u32 pkt_size][payload]`; control = `u32 0xFFFFFFFF` + `u32 ctrl_type` + body. `CTRL_RESIZE=1` body = HsRequestV2; `CTRL_FORCE_IDR=2` / `CTRL_EOS=3` body empty; `CTRL_RECONFIG=4` body = HsRequestV2 (runtime param change — receiver re-opens the decoder and sets `skip_until_key`, see the shared resize/reconfig handler in receiver.cpp).
- Coded payload = one access unit per packet (annex-B / OBU). Raw/RLE unchanged. 8082 remote RLE is connected **only** while `codec=rle` (connect/disconnect follows runtime codec switches).
- STAT| machine-readable status lines on stdout (parsed by the GUI): `STAT|k=v|k=v|...` with keys t/frames/fps/kbps/codec/hw/mode/src/dst/quality/record/svc/stage/err/port or `event=start|stop|error|applied|pong|stitch|auth|policy|svc` + `msg=` (stitch adds `state=waiting|local|remote` and `side=left|right|top|bottom`; `state=waiting` is emitted before the peer authorizes and must not be shown as a live session; the GUI renders the state in `drawStatPanel` and the side as its four-way switch; receiver `auth` adds `id/dev/ip/req/result`, with `result=allow|deny|timeout|cancelled`, and the GUI opens its approval modal). Receiver `ready` is `ready|port=8081|policy=<mode>` and appends `|record=bad|state=error` when the password record is unusable; a `error|msg=auth_config` follows it and is fatal/fail-closed. Each sidecar's real startup result is `STAT|event=svc|svc=gpu|ports|kvm|port=…|state=ok|fail|na|stage=none|socket|winsock|bind|listen|unsupported|err=<native code>`. The parser replaces its state per line, but not every line is a full snapshot: only periodic lines and `event=applied` carry the full key set — `start`/`stop`/`error`/`pong` carry subsets (sender `error` = `msg=` only; the receiver emits its own `start`/`stop`/`error`/`resize`/`reconfig`/`auth`/`policy` variants). The GUI special-cases event lines; check `parseStatLine` in app.cpp before changing emitter key sets. STAT lines are parsed on the GUI thread (`drainChildStats`): never call SDL from the stdout reader thread.
- Stitch file drop emits `STAT|event=drop|state=ready|sending|receiving|done|error|disabled|busy|items=…|failed=…|fallback=0|1|port=…|msg=…`. These lines are informational: the GUI logs them and must not treat them as a session start/stop/error (a failed drop does not end the stitch session).
- GUI→sender stdin line protocol (runtime reconfigure): `SETP|codec=…|hw=…|bitrate=…|quality=…|fps=…|scale=…|chroma=…` (any subset; keys map to the CLI flags; numeric values must be whole decimal numbers — parse with a strict whole-token check, never `atoi`; all-or-nothing validation, reply `STAT|event=applied|…` or `STAT|event=error|msg=bad_value_*`). `AUTH|password=…` answers a pending password prompt (taken verbatim, never echoed; ASCII case-folding happens only at the KDF step), `AUTH|cancel` withdraws it, and a bare line while the prompt is open is the interactive-console password path. `STITCH|side=left|right|top|bottom` switches a running stitch controller's edge (applied by the message loop within one 50 ms tick; hands control back first). `PING` → `STAT|event=pong`. `STOP|mivara` is the **shared owner-stop line** (sender and receiver): it ends the process through its normal cleanup path. It is longer than the 8-character password rule so a child waiting at the interactive password prompt can never mistake it for input, and it comes before the password branch for that reason.
- GUI→receiver stdin: `RX|reload` re-reads `config.ini` (policy/password changes) without restarting the listener; `AUTH|id=N|allow` / `AUTH|id=N|deny` answer a manual approval; `RX|disconnect` ends the active video session; `RX|quit` (and the shared `STOP|mivara`) shut the process down.
- Ports: 1900/udp SSDP, 8081/tcp video + authorization, 8082/tcp compute offload (`GPU_ACCEL_PORT`, session token required on connect and per request), 8083/tcp port inspector (`PORTS_SERVICE_PORT`, same token rule), 8084/tcp stitch KVM (`KVM_PORT`, `kvm.h`, same policy as 8081 and the same single active-session slot), 8085/tcp stitch file drop (`DROP_PORT`, token-gated by the active 8084 session; see below).
- **Stitch channel (8084, protocol v2):** `KvmHello` (16 B, magic `0x4D564B31` 'MVK1', `KVM_VERSION = 2`; `reserved[0]` = the peer's side from the controller's viewpoint + 1 (1 left / 2 right / 3 top / 4 bottom), used only to word the approval dialog — 0/unknown means right, so a zero-filled hello from an older build is not misread as "left") → then, by the receiver's 接收策略:
  - **open:** `KvmReply` (32 B: magic 'MVK1', version=2, status 0 ok / 1 version / 2 denied / 3 busy + target virtual-desktop x/y/w/h) immediately.
  - **password/manual:** `HsAuthStart` (the 8081 challenge, reused verbatim) → `HsRequestExtV3` (device name) → optional `HsAuthProof` → `HsResponseV2`; `HS_OK` is followed by the usual `KvmReply` with metrics. The proof binds this connection with purpose 2: `HMAC-SHA256(purpose_key, "Mivara/v1/auth-proof" ‖ 2 ‖ nonce ‖ KvmHello ‖ HsRequestExtV3)`. A missing/corrupt password record is refused before the challenge with `HsResponseV2(HS_ERR_AUTH_CONFIG)`. Identity and proof waits are bounded by a single handshake budget (hello 3 s, identity 10 s, proof 125 s — matching the controller's 120 s password prompt — 140 s total); a stalled peer is released and its source is cooled down.
  - The controller reads the first four bytes to tell the three cases apart (`KVM_MAGIC`, `TVHA_MAGIC`, `TVHS_MAGIC`). Version 1 peers are refused `KVM_ERR_VERSION`; there is no 8084-only consent path that bypasses the configured policy. Manual mode uses the **same** approval machinery as 8081 (`waitManualApproval`/`nativeManualPrompt`, 30 s timeout, repeated requests merged per IP+device+request type), not a second dialog. Only one approval prompt exists at a time across 8081 and 8084; a second device is answered BUSY rather than replacing the prompt the user is looking at. Only an explicit refusal arms the 60 s per-source cooldown — timeout, peer disconnect and prompt failure release the slot without one, and an allow arriving after the deadline is ignored.
  - `KvmEvent` (16 B: type 1 move / 2 button / 3 wheel / 4 key / 5 release-all / 6 ping / 7 pong). All `uint32` network byte order. `KvmHello.reserved[1]` and `KvmReply.reserved` negotiate `KVM_FEATURE_HEARTBEAT`: peers exchange PING/PONG every 3 s and disconnect after ~9 s without input. `kvmSendAll` never retries a blocking send after `WSAETIMEDOUT`: Winsock may already have queued an unreported prefix, and re-sending would duplicate bytes in the fixed 16-byte stream. Both sockets instead use a 2 s `SO_SNDTIMEO` (the controller's old 300 ms value made transient congestion tear the session down). The controller drain thread also monitors EOF/errors even when no input is being sent; local stop shuts down the socket before joining, and the target releases held input on EOF. The side itself is controller-only state (the target injects absolute coordinates), so switching needs no message. `HsRequestV2.mode` stays 0/1 — stitch never touches 8081, and `handleClientConnection` normalises any other mode to mirror.
- **Stitch file drop (opt-in, 8085):** `KVM_FEATURE_FILE_DROP = 2` in `KvmHello.reserved[1]` / `KvmReply.reserved`. The controller sets it only when `--file-drop 1` and the Medium-integrity `stitchcap.exe` helper is ready; the target echoes it only when `file_drop_accept=1`, the 8085 listener is up, and the session was authorized. On `KVM_OK` the target then sends **one marker + eight fixed `KvmEvent` frames** (`KVM_EV_DROP_INFO`: marker `a='MVKX'`, `b=1`, `c=8`; then `b` = one 32-bit token word). The controller reads this sequence *before* it starts `drainLoop()`, so the 16-byte event parser never sees a variable-length frame; an old controller never sets the bit and therefore never receives it. The token is a per-session 32-byte CSPRNG value installed in the 8085 gate before `KvmReply` is sent and cleared when the 8084 lease ends. 8085 is a separate TCP service (same process) with its own `DropHello` (72 B: token, transfer id, release point, item/byte counts), `DropReply` (16 B), and 16-byte frames (`MANIFEST`, `FILE_BEGIN`, `FILE_DATA`, `FILE_END`, `DONE`, `RESULT`, `ABORT`). The target writes to `%LOCALAPPDATA%\Mivara\Drop\<transfer>-<nonce>`, verifies per-file SHA-256, then copies the top-level items into the Explorer/Desktop folder under the release point; it never overwrites and never moves or deletes the source. A partial per-item commit is reported as an error with `items`/`failed` counts, not as `done`. Limits: 1000 items, 2 GiB total/file, 64 KiB chunks, 4 GiB per-session budget. The 200 ms post-crossing grace window that absorbs the helper's asynchronous `DragEnter` is controller-local state and adds no wire message. A NODRAG after Esc/DragLeave clears it, and `KVM_WM_DROP` re-checks `dropHelperDragLive()` before transferring (the hook's check alone is a TOCTOU); OLE `Drop` intentionally sends no NODRAG so the capture survives until the controller's posted drop message consumes it. A release inside the window is never resolved on arrival: it waits out the window and, while the helper has announced a drag but not finished the list (`dropHelperDragPending`, e.g. a slow CF_HDROP render), up to a 2 s hard cap, after which a capture starts the transfer or the pending state is dropped. Every left-button down discards the previous capture, and only a press that reached this desktop can adopt one. Both ends default to off; the channel is plaintext and the token is only admission control (see SECURITY.md).
- Approval STAT lines are shared by 8081 and 8084: `STAT|event=auth|state=pending|id=N|dev=…|ip=…|mode=manual|req=video|stitch` and `STAT|event=auth|state=done|id=N|result=allow|deny|timeout|cancelled`. The app shows the device name, address and request type; the same (IP, device, req) triple merges into one prompt, and only one merged waiter receives the allow — the others are refused. A prompt for a different device is refused with `HS_ERR_BUSY` while another prompt is open (the receiver serializes prompts); no `pending`/`done` line is emitted for it, and 8081 additionally emits `error|msg=peer_busy`.
- SSDP discovery: sender probes **per local NIC** over 3 rounds (~100 ms apart), each sending multicast + 255.255.255.255 + a directed per-NIC subnet broadcast (enterprise nets often drop multicast). Replies are keyed on the **datagram source address**, with the LOCATION IP probed only as a fallback (multi-homed receivers may advertise the wrong NIC). Receiver's LOCATION uses `getLocalIPForPeer(requester)` (same-subnet NIC). Receiver advertises `NAME: <hostname>`.
- Windows `SO_RCVTIMEO`/`SO_SNDTIMEO` take DWORD milliseconds, not `struct timeval` (POSIX). Passing a timeval silently gives ~5 ms timeouts.
- Sender and receiver must be the **same binary version** (protocol v3). Mismatched builds fail the handshake with an explicit error — never silently black-screen. A v1 stitch peer is refused the same way (`KVM_ERR_VERSION`), so an updated receiver cannot be driven by an old controller without passing the current policy.
