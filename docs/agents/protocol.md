# Protocol maintainer guide

Authoritative guidance for wire protocols, runtime control channels, discovery and network behavior. Read this file before changing those areas.

[Back to AGENTS.md](../../AGENTS.md)

## Protocol constants (defined in `src/proto.h`)

- Handshake over TCP 8081 (**protocol v3**, all u32 network byte order, magic `0x54564853` 'TVHS', `TVHS_VERSION = 3`):
  - Request (sender→receiver) `HsRequestV2` **48 bytes**: magic, version=3, width, height, fps, mode, codec, codec_flags, bitrate_kbps, quality, gop_frames, reserved.
  - Challenge (receiver→sender) `HsAuthStart` **64 bytes**: magic `0x54564841` 'TVHA', version=2, mode (`AUTH_MODE_OPEN/PASSWORD/MANUAL`), kdf_iter, salt[16], nonce[32]. Sent for every policy; the salt/iter are filled (and meaningful) only in password mode.
  - Identity (sender→receiver) `HsRequestExtV3` **48 bytes**: magic 'TVHX', version=2, device[32] (UTF-8 hostname), flags, reserved.
  - Proof (sender→receiver, password only) `HsAuthProof` **40 bytes**: magic 'TVHA', version=2, proof[32].
  - Response (receiver→sender) `HsResponseV2` **36 bytes**: magic, version=3, recv_width, recv_height, status, codec, codec_flags, reserved[2].
  - Token (receiver→sender, `HS_OK` only) `HsResponseExtV3` **44 bytes**: magic `0x54564852` 'TVHR', version=2, token[32], flags.
  - `mode`: 0 = mirror, 1 = extend. `codec`: 0=raw 1=rle 2=h264 3=h265 4=av1. `status`: 0=ok 1=version 2=codec 3=dims 4=decoder 5=legacy 6=busy 7=auth 8=auth_timeout 9=denied 10=auth_config.
  - Receiver peeks 4 bytes first: non-TVHS magic ⇒ legacy peer, explicit error (no black screen). A pre-v3 request is answered `HS_ERR_VERSION` **before** the authorization exchange, so an old sender cannot bypass the policy.
  - Authorization is enforced at the receiver only. The proof is purpose-separated (`auth.h`):
    `purpose_key = HMAC-SHA256(PBKDF2(fold(pw), salt, iter), "Mivara/v1/auth-key" ‖ purpose)` and
    `proof = HMAC-SHA256(purpose_key, "Mivara/v1/auth-proof" ‖ purpose ‖ nonce ‖ raw HsRequestV2 ‖ raw HsRequestExtV3)`,
    with `purpose = 1` for 8081 video, `2` for 8084 stitch and `3` for 8086 file transfer. The 8086 proof binds the raw 16-byte file hello + HsRequestExtV3 instead of HsRequestV2. `fold` is ASCII-only and locale-independent: `A`–`Z` become `a`–`z`, every other byte is unchanged, so passwords are case-insensitive. Record creation (`mivaraPasswordKey`), the 8081 sender and the 8084 stitch controller must all fold before PBKDF2; the receiver never sees the plaintext and never folds the stored record. The wire carries no password and the receiver stores only salt + PBKDF2 output + iter. New records use `MIVARA_AUTH_DEFAULT_ITER` (300000); existing records keep the count they were created with. Accepted `kdf_iter` is bounded by `HS_KDF_ITER_MIN/MAX` (10000–1000000); anything else is a corrupt record, refused `HS_ERR_AUTH_CONFIG` rather than downgraded. `HsResponseV2` is sent for denial/timeout/bad proof; a password policy whose record is missing or malformed refuses every connection (`HS_ERR_AUTH_CONFIG`) and never falls back to open or to a prompt. Purpose separation and the higher iteration count reduce cross-port replay and raw-key reuse but do **not** remove offline guessing or the credential-equivalence of a leaked `config.ini` — see SECURITY.md.
  - **Display-size probe (no version bump):** a normal `HsRequestV2` with `width=0 && height=0` asks only for `HsResponseV2.recv_width/recv_height`; the receiver answers with `status=HS_ERR_DIMS` and returns before creating a window, a decoder or an authorization exchange. The reply comes from a cache refreshed by the receiver's main thread (at most once per second while idle and again before/after every session, so a monitor change or dock replug is picked up without touching SDL from a worker), in physical pixels. No window appears and no client stats are recorded. Extend mode uses it to size the VDD before the real handshake.
  - **Session token:** an authorized 8081 session receives a random 32-byte, per-session token. The 8082 compute service and the 8083 port inspector read 32 bytes on connect **and re-check the token before every request** (including before 8083's expensive port listing and its kill operation), so a connection opened during a session loses access on its next request once the session ends, and a new connection presenting the old token is refused. `mivaraSessionTokenClearIf()` clears only the ending session's token.
  - **One session per process:** 8081 and 8084 share one active-session slot in `auth.cpp`. While either port has a session, the other answers `HS_ERR_BUSY` (8084 sends `HsResponseV2(HS_ERR_BUSY)`). An unauthenticated handshake never holds the slot: 8081/8084 pre-check the owner before the challenge, and claim it only after authorization succeeds — or, in manual mode, just before the prompt (a human decision must not be stolen by the other port).
- Stream packets: `[u32 pkt_size][payload]`; control = `u32 0xFFFFFFFF` + `u32 ctrl_type` + body. `CTRL_RESIZE=1` body = HsRequestV2; `CTRL_FORCE_IDR=2` / `CTRL_EOS=3` body empty; `CTRL_RECONFIG=4` body = HsRequestV2 (runtime param change — receiver re-opens the decoder and sets `skip_until_key`, see the shared resize/reconfig handler in receiver.cpp).
- Coded payload = one access unit per packet (annex-B / OBU). Raw/RLE unchanged. 8082 remote RLE is connected **only** while `codec=rle` (connect/disconnect follows runtime codec switches).
- STAT| machine-readable status lines on stdout (parsed by the GUI): `STAT|k=v|k=v|...` with keys t/frames/fps/kbps/codec/hw/mode/src/dst/quality/record/svc/stage/err/port or `event=start|stop|error|applied|pong|stitch|auth|policy|svc` + `msg=` (stitch adds `state=waiting|local|remote|reconnecting` and `side=left|right|top|bottom`; `state=waiting` is emitted before the peer authorizes and must not be shown as a live session; `state=reconnecting` keeps the session alive (and its Stop button reachable) while `kvmRunControllerResilient` retries and adds `reason=peer_closed|recv_error|select_error|heartbeat_timeout|send_error|protocol_event`, `err=<wsa>`, `retry=N`, `delay_ms=D`; it is not a new history record (each retry also emits the normal `state=waiting` before its handshake, which the GUI rewrites to `reconnecting` while the outage is active); the GUI renders the state in `stitchSessionHint()` on the home stitch card (`drawHomeStitchCard()`; stitch never enters `SCR_STREAMING` — `drawStatPanel()` is mirror/extend-only) and the side as that card's four-way `BTN_STITCH_SWITCH_*` switch; receiver `auth` adds `id/dev/ip/req/result`, with `result=allow|deny|timeout|cancelled`, and the GUI opens its approval modal). Receiver `ready` is `ready|port=8081|policy=<mode>` and appends `|record=bad|state=error` when the password record is unusable; a `error|msg=auth_config` follows it and is fatal/fail-closed. Each sidecar's real startup result is `STAT|event=svc|svc=gpu|ports|kvm|port=…|state=ok|fail|na|stage=none|socket|winsock|bind|listen|unsupported|err=<native code>`. The parser replaces its state per line, but not every line is a full snapshot: only periodic lines and `event=applied` carry the full key set — `start`/`stop`/`error`/`pong` carry subsets (sender `error` = `msg=` only; the receiver emits its own `start`/`stop`/`error`/`resize`/`reconfig`/`auth`/`policy` variants). The GUI special-cases event lines; check `parseStatLine` in app.cpp before changing emitter key sets. STAT lines are parsed on the GUI thread (`drainChildStats`): never call SDL from the stdout reader thread.
- Stitch file drop emits `STAT|event=drop|state=ready|sending|receiving|done|error|disabled|busy|items=…|failed=…|fallback=0|1|port=…|msg=…`. These lines are informational: the GUI logs them and must not treat them as a session start/stop/error (a failed drop does not end the stitch session). The independent 8086 service likewise emits only informational `STAT|event=files|state=…` lines; app-client directory/progress results use the structured `ftClientPoll` queue, never STAT or stdin.
- GUI→sender stdin line protocol (runtime reconfigure): `SETP|codec=…|hw=…|bitrate=…|quality=…|fps=…|scale=…|chroma=…` (any subset; keys map to the CLI flags; numeric values must be whole decimal numbers — parse with a strict whole-token check, never `atoi`; all-or-nothing validation, reply `STAT|event=applied|…` or `STAT|event=error|msg=bad_value_*`). `AUTH|password=…` answers a pending password prompt (taken verbatim, never echoed; ASCII case-folding happens only at the KDF step), `AUTH|cancel` withdraws it, and a bare line while the prompt is open is the interactive-console password path. `STITCH|side=left|right|top|bottom` switches a running stitch controller's edge (applied by the message loop within one 50 ms tick; hands control back first). `PING` → `STAT|event=pong`. `STOP|mivara` is the **shared owner-stop line** (sender and receiver): it ends the process through its normal cleanup path. It is longer than the 8-character password rule so a child waiting at the interactive password prompt can never mistake it for input, and it comes before the password branch for that reason.
- GUI→receiver stdin: `RX|reload` re-reads `config.ini` (policy/password changes) without restarting the listener; `AUTH|id=N|allow` / `AUTH|id=N|deny` answer a manual approval; `RX|disconnect` ends the active video session; `RX|quit` (and the shared `STOP|mivara`) shut the process down.
- Ports: 1900/udp SSDP, 8081/tcp video + authorization, 8082/tcp compute offload (`GPU_ACCEL_PORT`, session token required on connect and per request), 8083/tcp port inspector (`PORTS_SERVICE_PORT`, same token rule), 8084/tcp stitch KVM (`KVM_PORT`, `kvm.h`, same policy as 8081 and the same single active-session slot), 8085/tcp stitch file drop (`DROP_PORT`, token-gated by the active 8084 session; see below), 8086/tcp independent two-way file transfer (`FILEXFER_PORT`, `filexfer.h`, separate opt-in + purpose 3 + own single-client slot).
- **Stitch channel (8084, protocol v2):** `KvmHello` (16 B, magic `0x4D564B31` 'MVK1', `KVM_VERSION = 2`; `reserved[0]` = the peer's side from the controller's viewpoint + 1 (1 left / 2 right / 3 top / 4 bottom), used only to word the approval dialog — 0/unknown means right, so a zero-filled hello from an older build is not misread as "left") → then, by the receiver's 接收策略:
  - **open:** `KvmReply` (32 B: magic 'MVK1', version=2, status 0 ok / 1 version / 2 denied / 3 busy + target virtual-desktop x/y/w/h) immediately.
  - **password/manual:** `HsAuthStart` (the 8081 challenge, reused verbatim) → `HsRequestExtV3` (device name) → optional `HsAuthProof` → `HsResponseV2`; `HS_OK` is followed by the usual `KvmReply` with metrics. The proof binds this connection with purpose 2: `HMAC-SHA256(purpose_key, "Mivara/v1/auth-proof" ‖ 2 ‖ nonce ‖ KvmHello ‖ HsRequestExtV3)`. A missing/corrupt password record is refused before the challenge with `HsResponseV2(HS_ERR_AUTH_CONFIG)`. Identity and proof waits are bounded by a single handshake budget (hello 3 s, identity 10 s, proof 125 s — matching the controller's 120 s password prompt — 140 s total); a stalled peer is released and its source is cooled down.
  - The controller reads the first four bytes to tell the three cases apart (`KVM_MAGIC`, `TVHA_MAGIC`, `TVHS_MAGIC`). Version 1 peers are refused `KVM_ERR_VERSION`; there is no 8084-only consent path that bypasses the configured policy. Manual mode uses the **same** approval machinery as 8081 (`waitManualApproval`/`nativeManualPrompt`, 30 s timeout, repeated requests merged per IP+device+request type), not a second dialog. Only one approval prompt exists at a time across 8081 and 8084; a second device is answered BUSY rather than replacing the prompt the user is looking at. Only an explicit refusal arms the 60 s per-source cooldown — timeout, peer disconnect and prompt failure release the slot without one, and an allow arriving after the deadline is ignored.
  - `KvmEvent` (16 B: type 1 move / 2 button / 3 wheel / 4 key / 5 release-all / 6 ping / 7 pong / 8 drop-info / 9 rdrag / 10 drag-info / 11 drag-text / 12 drag-icon-info / 13 drag-icon-data / 14 drag-image-info / 15 drag-image-data). All `uint32` network byte order. `KvmHello.reserved[1]` and `KvmReply.reserved` negotiate `KVM_FEATURE_HEARTBEAT`: peers exchange PING/PONG every 3 s (`KVM_HEARTBEAT_INTERVAL_MS`) and disconnect after 9 s without input (`KVM_HEARTBEAT_TIMEOUT_MS`). Both receive loops also detect a local suspend/starve gap (>3 s between iterations) and restart the receive clock instead of mistaking a laptop resume for a dead peer. `kvmSendAll` never retries a blocking send after `WSAETIMEDOUT`: Winsock may already have queued an unreported prefix, and re-sending would duplicate bytes in the fixed 16-byte stream. A failed PING/PONG/event send therefore ends that session; both sockets use a 2 s `SO_SNDTIMEO` to ride out an ordinary buffer stall. The controller drain thread also monitors EOF/errors even when no input is being sent; local stop shuts down the socket before joining, and the target releases held input on EOF. After an established session loses its socket (interface change, peer restart, Wi-Fi roam), `kvmRunControllerResilient` emits `state=reconnecting` and reconnects with 1/2/4/8/16/30 s backoff until the owner stops it; a `STITCH|side=…` switch received during the outage is applied to the next hello. Failures before the first session (connect refused, busy, denied) keep the old one-shot error behaviour. The side itself is controller-only state (the target injects absolute coordinates), so switching needs no message. `HsRequestV2.mode` stays 0/1 — stitch never touches 8081, and `handleClientConnection` normalises any other mode to mirror.
- **Stitch file drop (opt-in, 8085):** `KVM_FEATURE_FILE_DROP = 2` in `KvmHello.reserved[1]` / `KvmReply.reserved`. The controller sets it only when `--file-drop 1` and the Medium-integrity `stitchcap.exe` helper is ready; the target echoes it only when `file_drop_accept=1`, the 8085 listener is up, and the session was authorized. On `KVM_OK` the target then sends **one marker + eight fixed `KvmEvent` frames** (`KVM_EV_DROP_INFO`: marker `a='MVKX'`, `b=1`, `c=8`; then `b` = one 32-bit token word). The controller reads this sequence *before* it starts `drainLoop()`, so the 16-byte event parser never sees a variable-length frame; an old controller never sets the bit and therefore never receives it. The token is a per-session 32-byte CSPRNG value installed in the 8085 gate before `KvmReply` is sent and cleared when the 8084 lease ends. 8085 is a separate TCP service (same process) with its own `DropHello` (72 B: token, transfer id, release point, item/byte counts), `DropReply` (16 B), and 16-byte frames (`MANIFEST`, `FILE_BEGIN`, `FILE_DATA`, `FILE_END`, `DONE`, `RESULT`, `ABORT`). The target writes to `%LOCALAPPDATA%\Mivara\Drop\<transfer>-<nonce>`, verifies per-file SHA-256, then copies the top-level items into the Explorer/Desktop folder under the release point; it never overwrites and never moves or deletes the source. A partial per-item commit is reported as an error with `items`/`failed` counts, not as `done`. Limits: 1000 items, 2 GiB total/file, 64 KiB chunks, 4 GiB per-session budget. The 200 ms post-crossing grace window that absorbs the helper's asynchronous `DragEnter` is controller-local state and adds no wire message. A NODRAG after Esc/DragLeave clears it, and `KVM_WM_DROP` re-checks `dropHelperDragLive()` before transferring (the hook's check alone is a TOCTOU); OLE `Drop` intentionally sends no NODRAG so the capture survives until the controller's posted drop message consumes it. A release inside the window is never resolved on arrival: it waits out the window and, while the helper has announced a drag but not finished the list (`dropHelperDragPending`, e.g. a slow CF_HDROP render), up to a 2 s hard cap, after which a capture starts the transfer or the pending state is dropped. Every left-button down discards the previous capture, and only a press that reached this desktop can adopt one. Both ends default to off; the channel is plaintext and the token is only admission control (see SECURITY.md).
- **8085 liveness flag:** `dropSendFiles`'s fourth parameter is a true=continue `running` flag, fed by the controller's `g_drop_run` (kvm.cpp): `startFileDrop` sets it before every transfer, and KVM_WM_PANIC / KVM_WM_DISCONNECT / teardown clear it to abort. Never pass an inverted "cancel" flag here — the historical `g_drop_cancel` bug made `connectSocket` fail its very first `!running` check on every release, so the channel never sent a single DropHello. `DROP_PORT` is overridable at compile time for loopback diagnostics only (production stays 8085), mirroring `FILEXFER_PORT`. Field diagnostics: `MIVARA_DROP_TRACE=1` in the controller's environment logs every helper pipe message to `%TEMP%\mivara-dropctl-trace.log`, and `MIVARA_STITCHCAP_TRACE=1` (inherited by the helper) logs its OLE callbacks and pipe writes to `%TEMP%\mivara-stitchcap-trace.log`; both default off. The gitignored `test/` harnesses are `dropcap_e2e.cpp` (a real OLE drag onto the strip — the harness must pump the press so the thread queue's button state is set, and must generate real motion events rather than SetCursorPos, or OLE parks the drag on its initial target), `dropwire_e2e.cpp` (loopback 8085 including the running=false regression and a wrong-token refusal), `stitchloop_e2e.cpp` (the real controller against a fake in-process target on 18084/18085 that never injects input), and `stitchreconnect_e2e.cpp` (the real `kvmRunControllerResilient` against a fake 18084 target that drops the first session; it asserts the second hello keeps a mid-outage side switch and that the reconnected session answers a heartbeat PING). Every `test/` harness is local-only: gitignored and never built by `make check`.
- **Reverse drag copy (target → controller):** `KVM_FEATURE_REVERSE_DROP = 4` in `KvmHello.reserved[1]` / `KvmReply.reserved`. The controller advertises it when its own `file_drop_accept=1` (sender `--accept-files`), and the target echoes it when its own `file_drop_send=1` (receiver `--file-drop`, `KvmTargetAuth.file_send`), the 8085 listener is up and the session was authorized. The 32-byte token is generated and sent (the same 1+8 `KVM_EV_DROP_INFO` frames) when **either** direction is enabled (`drop_ok || reverse_ok`), so a reverse-only session never runs with an all-zero token; the controller reads it when `g_drop_ready || g_reverse_ok` and installs its own 8085 gate + `dropServiceRun` for reverse reception. The target starts the same `stitchcap.exe` on the edge FACING the controller (opposite side) plus a watcher thread that emits `KVM_EV_RDRAG = 9` (`a=1` drag announced, `a=0` cancelled) and, once the OLE Drop fires, sends the captured files to the controller's reverse listener (8087) with `DropHello.flags = DROP_FLAG_REVERSE = 1`; watcher, PONG and heartbeat PING writes are serialized with `tx_mtx`. The controller's drainLoop accepts `KVM_EV_RDRAG` only when reverse was negotiated; while a reverse drag is live it suppresses back-crossing so the target's OLE drag can finish, and on release it forwards the UP (completing the target's OLE Drop) and hands control back. The receiving `dropWorker` resolves a reverse destination from `GetCursorPos` (its own desktop edge after leaveRemote) instead of `hello.x/y`, falling back to `Downloads\Mivara`. **The controller's reverse listener runs on `DROP_REVERSE_PORT` = 8087, advertised in `KvmHello.reserved[1]` bits 16..31** (features stay in the low bits, which is all an old peer bit-tests). Never reuse 8085 there: a controller commonly also runs `receiver.exe`, which owns 8085, so the bind fails and the token ends up installed in a process that does not serve the port — every reverse transfer is then refused `DROP_ERR_AUTH`. A rejected gate reports `STAT|event=drop|state=gate_reject|port=…|active=…|epoch=…` (never the token bytes).
- **Drag ghost (visual only; name frames need no negotiation):** the controller emits `KVM_EV_DRAG_INFO = 10` (`a=1` begin, `b` item count, `c` number of text frames; `a=0` end) followed by that many `KVM_EV_DRAG_TEXT = 11` frames, each carrying 12 raw UTF-8 bytes in `a`/`b`/`c` (the htonl/ntohl round-trip preserves the bytes). The target draws a rounded card with the file name next to the injected cursor via a layered `UpdateLayeredWindow` window (no message pump needed on the session thread) and hides it on the end frame or session exit. Older targets ignore unknown event types, so the **name** frames require no capability bit. The card also shows the dragged item's own shell image: the controller advertises `KVM_FEATURE_DRAG_ICON = 8` in `KvmHello.reserved[1]`, a target that understands the image frames echoes it in `KvmReply.reserved`, and only then does the controller emit `KVM_EV_DRAG_ICON_INFO = 12` (`a=width`, `b=height`, `c=DATA frame count`) followed by `KVM_EV_DRAG_ICON_DATA = 13` frames carrying 12 raw BGRA bytes per `a`/`b`/`c`. Payload bytes follow the same per-direction convention as `DRAG_TEXT`: queued controller events are byte-swapped field by field by the drain thread, while the reverse watcher writes them untouched. The source extracts the image with `IShellItemImageFactory` (thumbnail when a provider exists, otherwise the icon) away from the input loop and with a bounded wait (controller worker 800 ms, target reverse watcher 250 ms), so a stalled network/cloud provider cannot delay input, the 8085 copy or session teardown; it caps the icon at 48x48 (the receiver's frame cap is shared with the real-image path: 2,048 per dimension and 36,864 pixels; oversized/incomplete sequences fall back to the page glyph), and skips the icon rather than crowding key/button events out of the ring. The controller's drain thread sends every queued event in one batch rather than one per `select` tick, so a 769-frame icon burst cannot sit in front of mouse/button events for seconds. A reverse drag uses the same icon frames target→controller, gated on the controller's hello bit (the forward direction additionally requires the target's `KvmReply` echo). The target re-sends `DRAG_INFO`/`DRAG_TEXT` (and then the icon) once `FILES_END` publishes the list if the first poll saw an empty selection, and treats `NODRAG` as the end of the drag (discarding the helper's sticky `drag_seen`) so the next reverse drag is announced normally. **Real source drag image (preferred):** `KVM_FEATURE_DRAG_IMAGE = 16` is advertised by the controller in the hello and echoed by a target that understands `KVM_EV_DRAG_IMAGE_INFO = 14` / `DATA = 15`. The source `stitchcap.exe` reads the shell's `DragImageBits` from the OLE data object during `DragEnter`. After OLE marshals it, the HGLOBAL is `u32 width, u32 height, i32 offset_x, i32 offset_y`, a 4/8-byte process-local HBITMAP slot, then `width*height` premultiplied BGRA pixels at the tail in the DIB's **bottom-up** row order (the handle is invalid across processes, the pixels survive; `stitchcap.exe` swaps whole rows to top-down before forwarding, so a 180-degree-looking ghost is a bug). The helper downsizes above `DROP_DRAG_IMAGE_MAX_PIXELS` (36,864 px), sends `IMG_BEGIN`/`IMG_CHUNK` (hex)/`IMG_END` over its pipe, and the controller (or the target's reverse watcher) forwards `DRAG_IMAGE_INFO` (`a = width | offset_x << 16`, `b = height | offset_y << 16`, `c = DATA frames`) followed by `DATA` (12 premultiplied BGRA bytes per frame, same per-direction convention as the icon). The receiver draws the image's top-left at `cursor - offset`, exactly like `IDropTargetHelper`; a complete image replaces the reconstructed card, a missing/incomplete one leaves the icon/name card. One image is at most 12,288 DATA frames; the ring is 16,384 slots and the drain thread sends a queued burst in one batch. Reverse uses the same frames target→controller, gated on the controller's hello bit and the target's `KvmReply` echo. Never put anything security-relevant in these frames; an old peer never sets the bit and never sees them. **Reverse uses the same name frames in the opposite direction**: the target's watcher sends `DRAG_INFO`/`DRAG_TEXT` when its helper announces a reverse drag, and the controller renders the ghost next to its own cursor. A reverse drag crossing back **carries the file**: `leaveRemote(..., keepHeldInput=true)` returns control without `KVM_EV_RELEASE_ALL` (the target's OLE drag must stay alive), the local release forwards only the button-up so the target's OLE `Drop` fires, and the controller resolves the destination from `GetCursorPos` at hello time — so the icon lands where the user let go. Panic/disconnect while carrying back sends `RELEASE_ALL` so the peer never keeps a stuck button. Both directions are copy-only and share the same token; older peers never negotiate the bit and behave as before. Back-crossing a left-button drag in either direction additionally requires an accumulated ~24 px pushback (`KVM_BACK_DRAG_HYSTERESIS`) so a natural pullback no longer cancels the copy.
- **Independent file transfer (opt-in, 8086, protocol v2):** `FtHello`/`FtReply` are 16 B (`FILEXFER_MAGIC` 'MVF1', `FILEXFER_VERSION=2`); **both ends must be the same build** (v1 peers get `FT_ERR_VERSION`). Open replies immediately; password/manual reuse the standard challenge/identity/proof/`HsResponseV2`, then send `FtReply` after HS_OK. The proof uses purpose 3 and binds raw hello + identity. `file_transfer_accept=0` answers FT_ERR_DISABLED before authorization; the enabled flag is re-checked before every request. After admission and before the request loop the service sends exactly one INFO frame (length-prefixed device name, sanitized ≤31 bytes). The client reads it after BOTH handshake success paths (open returns early from the reply parser) and before emitting READY; a missing/garbled INFO is a protocol failure. The service owns one client slot independent of 8081/8084 and its listener is currently AF_INET/IPv4-only. The app client accepts only numeric IP literals (`AI_NUMERICHOST`/`AI_NUMERICSERV`) and rejects hostnames before starting the worker, so no DNS lookup can block `ftClientStop`'s join. Subsequent 16 B frames carry magic, u16 version/type, u32 payload length and reserved, all network order, with a 4 MiB frame ceiling. HOME/ROOTS/LIST return canonical UTF-8 paths and bounded directory entries; a listing entry is `flags(u8: bit0 directory, bit1 hidden) + name + size(u64) + mtime(u64 unix seconds, 0=unknown, ≤FILEXFER_MAX_MTIME)`. Hidden is a display hint only. PUT_BEGIN carries destination directory + one-component name + u64 size; GET carries an absolute file path; MKDIR carries parent directory + one-component name and RESULT returns the created absolute path. DATA uses 64 KiB chunks, END carries SHA-256, RESULT carries status, ABORT rolls back the temporary file. Paths are length-prefixed, never line-delimited, and capped at `FILEXFER_MAX_PATH_BYTES` = 4096 bytes. An authorized but idle connection is kept for up to 30 minutes (TCP keepalive detects a vanished peer; shutdown is polled every second). Single regular file per operation, max 64 GiB / 1000 listed entries; symlink/reparse/special files are skipped. Wire names use a platform-independent rule: one UTF-8 component, at most `FILEXFER_MAX_NAME_BYTES` = 1024 bytes, rejecting `/`, `\`, NUL, control characters, `.` and `..`; local filesystem rules (Windows `<>:"|?*`, reserved names, trailing dot/space, 255 UTF-16 units) apply only when creating a local file or folder, and a locally invalid wire name is a recoverable `FT_ERR_PATH` (the connection stays open). A Windows client therefore decodes a POSIX `a:b` listing but reports a local path error on download or mkdir. Receivers canonicalize the base directory once, pin it with a handle, walk child directories without following links, create an exclusive temporary file relative to that handle, verify size/hash, and commit with no replacement (collision names gain ` (1)` etc., with the stem truncated on a full UTF-8 character boundary to the target filesystem's component limit). MKDIR is handle-relative too: POSIX `mkdirat`, Windows `NtCreateFile(RootDirectory=…, FILE_CREATE|FILE_DIRECTORY_FILE)`; the pinned parent handle is opened with `FILE_ADD_SUBDIRECTORY` on Windows, and an existing name returns `FT_ERR_EXISTS` without replacing it. A same-directory temporary-name race remains if the directory is concurrently writable; source files are never moved or deleted. The app client runs on one worker and exposes bounded structured state/list/progress/complete/info events to SDL; it holds one pending operation, so multi-select is a GUI-side queue that starts the next item only when the client is idle. Cancelling an upload sends ABORT and keeps the connection reusable; a download cannot be stopped in-band (the sender never reads while streaming), so it closes the connection. Stop also releases password waits and joins the worker. Everything after authorization is plaintext.
- Approval STAT lines are shared by 8081 and 8084: `STAT|event=auth|state=pending|id=N|dev=…|ip=…|mode=manual|req=video|stitch|files` and `STAT|event=auth|state=done|id=N|result=allow|deny|timeout|cancelled`. The app shows the device name, address and request type; the same (IP, device, req) triple merges into one prompt, and only one merged waiter receives the allow — the others are refused. A prompt for a different device is refused with `HS_ERR_BUSY` while another prompt is open (the receiver serializes prompts); no `pending`/`done` line is emitted for it, and 8081 additionally emits `error|msg=peer_busy`.
- SSDP discovery: sender probes **per local NIC** over 3 rounds (~100 ms apart), each sending multicast + 255.255.255.255 + a directed per-NIC subnet broadcast (enterprise nets often drop multicast). Replies are keyed on the **datagram source address**, with the LOCATION IP probed only as a fallback (multi-homed receivers may advertise the wrong NIC). Receiver's LOCATION uses `getLocalIPForPeer(requester)` (same-subnet NIC). Receiver advertises `NAME: <hostname>`.
- Windows `SO_RCVTIMEO`/`SO_SNDTIMEO` take DWORD milliseconds, not `struct timeval` (POSIX). Passing a timeval silently gives ~5 ms timeouts.
- Sender and receiver must be the **same binary version** (protocol v3). Mismatched builds fail the handshake with an explicit error — never silently black-screen. A v1 stitch peer is refused the same way (`KVM_ERR_VERSION`), so an updated receiver cannot be driven by an old controller without passing the current policy.
